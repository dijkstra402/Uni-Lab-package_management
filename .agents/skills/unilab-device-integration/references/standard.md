## 标准资产

仓库根目录中的 `device_templates_actions.csv` 是动作、参数和状态接口的唯一事实来源：

- `packages/<device_id>/<device_id>/<device_id>.py`：设备大类的标准接口模板。
- `packages/<device_id>/<device_id>/<device_id>_plc.py`：同一接口的 PLC/OPC UA 实现。
- `generate_plc_drivers.py`：根据实时 CSV 批量生成 PLC 实现。
- `base_opcua_client.py`：OPC UA 连接、节点注册、读写、订阅和缓存。
- `AI4C.py`：复杂 OPC UA 交互的参考实现，不作为所有设备必须照搬的通用接口。

标准模板定义“设备能做什么”，具体驱动定义“如何通过当前协议做到”。上层工作流只能依赖前者。

## CSV 字段

| 字段 | 含义 | 规则 |
| --- | --- | --- |
| `设备大类` | 中文类别名 | 同一 `device_id` 内保持一致 |
| `device_id` | 稳定英文类别 ID | 使用 `snake_case`，不能包含品牌型号 |
| `类型` | 接口种类 | 只能是 `action` 或 `property` |
| `英文名` | Python 接口名 | 使用有效 `snake_case` 标识符 |
| `中文描述` | 展示与语义说明 | 简短、明确、同类设备通用 |
| `参数(名:类型)` | 动作参数或属性类型 | 无参动作留空；有参动作用 `name:type`；属性直接写类型 |
| `PLC节点` | 逻辑 PLC 节点名 | 不是部署现场的 OPC UA NodeId |
| `交互模式` | PLC 交互方式 | `写设定值`、`写触发→等完成→复位` 或 `读状态` |

当前生成器支持动作最多一个参数，基础类型为 `bool`、`int`、`float`、`str`。需要多参数、枚举、数组或结构体时，先扩展 CSV 结构和生成器，并把它视为标准变更。

同一 `device_id` 内，`类型 + 英文名` 必须唯一。动作参数名应表达业务含义，不使用 `value` 等弱语义名称。

## 设备大类决策

优先用能力和工艺语义匹配类别：

1. 设备主要功能是否与现有大类一致？
2. 现有动作和状态能否表达真实能力？
3. 差异是否只是品牌协议、寄存器地址、量程或单位？如果是，复用现有大类。
4. 差异是否改变工作流语义？只有这种差异才考虑扩展接口或新增大类。

不要为“某品牌蠕动泵”新增大类。应使用 `peristaltic_pump` 标准，并为具体实现分配唯一设备 ID，例如 `vendor_model_peristaltic_pump`。

修改已有大类时，优先新增并保持兼容。重命名、删除接口、改变参数或返回类型都属于破坏性变更。不得因单个型号不支持某项能力而删除整个大类的标准接口。

## 直连驱动

直连表示 Uni-Lab 进程直接连接设备控制器，底层可以是串口、TCP、HTTP、Modbus 或厂商 SDK。具体驱动应：

- 继承或严格实现选定大类接口。
- 把标准动作映射为协议命令，把标准属性映射为查询结果或可靠缓存。
- 建立连接时验证设备身份，释放时关闭连接。
- 实现超时、帧边界、校验、有限重试和断线处理。
- 明确寄存器地址、字节序、缩放、单位和数据刷新策略。
- 将协议值规范化为 CSV 定义的 Python 类型和标准单位。
- 不在属性读取中触发有副作用的动作，不记录密码、令牌等敏感信息。

## PLC 与 OPC UA 驱动

PLC 负责实时顺序、联锁和执行器控制；Uni-Lab 负责以标准接口下发任务和读取状态。OPC UA 是连接 PLC 的一种协议，不等于 PLC 架构本身。

- 有参动作：`set_temperature(temperature)` → 写 `温度设置`。
- 无参动作：`start()` → 写 `启动触发=True` → 等 `启动完成=True` → 写 `启动触发=False` → 等 `启动完成=False`。
- 属性：`current_temperature` → 读 `当前温度`。

需要区分两份 CSV：

1. `device_templates_actions.csv`：跨设备的接口与逻辑节点标准。
2. 现场节点映射 CSV：把逻辑名称映射到 PLC 的真实 NodeId，供 `load_nodes_from_csv` 加载，通常包含 `Name`、`EnglishName`、`NodeType`、`DataType`、`NodeId` 等字段。

生成器是批量写操作。运行前检查工作区，运行后检查全部差异并执行接口校验。不得长期手工维护自动生成的 `_plc.py`。

## 验收清单

- 已从实时 CSV 选择或定义 `device_id`。
- 标准模板、直连实现和 PLC 实现的接口名与类型一致。
- 具体驱动使用唯一设备 ID，且没有把品牌写入设备大类。
- 每个动作都有协议命令或 PLC 节点映射。
- 每个属性都有数据来源、类型、单位和刷新策略。
- 设置值具备范围检查，通信具备有限超时。
- 错误信息能定位连接、协议、设备拒绝或 PLC 完成超时。
- 安全联锁和急停逻辑没有被绕过。
- 已运行 `device_standard.py --validate --check-code <device_id>`；全量审计时才使用 `--check-code all`。
- 已运行目标包的 `unilab --check_mode`；环境缺少 `unilabos` 时明确记录未执行原因。
- 有硬件时验证连接、动作、状态、异常路径和断线恢复；无硬件时明确标注仅完成静态或模拟验证。
